StayOS PMS Main PMS Screen (Application Shell) Backend Workflow Documentation Document Type: Backend Workflow Module: Main PMS Screen / Shell Status: Draft v1.0 1. Session & Login Login authenticates against app_user (validated against the Auth service's credential store, not a password column in app_user itself) and issues a JWT containing: user_id, client_id, role_id, and role_type. This is the only login in the application — Configuration does not have (and does not need) its own login screen, since it's reached as an authenticated route within the same session, not a separate application. 2. Module Registry & Role-Based Visibility Two small new tables support this — neither existed in the Configuration migration, since menu visibility wasn't previously a concern: Module Registry Table: module_registry CREATE Seeded once, not user-editable through the UI: one row per of the 11 modules (module_key, display_name, icon_key, sort_order, is_built). UPDATE is_built is flipped to true by an engineer (via a migration or admin script) once a module actually ships — this is what drives the "Coming Soon" placeholder vs. real content. DELETE Not deletable through the UI — this is an application-level constant table, not tenant data. BUSINESS RULES / SIDE EFFECTS GET /modules reads this table joined with role_module_access (below) to build the sidebar for the current user. Role Module Access Table: role_module_access CREATE One row per (role_id, module_key) that a role is allowed to see; requires a valid role_id and an existing module_key. UPDATE Changing access takes effect on the affected users' next sidebar fetch (GET /modules), not necessarily mid-session unless the shell polls or the client re-fetches on focus. DELETE Deleting a row revokes that role's access to that module; the sidebar then shows it locked, not hidden (per the UI/UX doc). BUSINESS RULES / SIDE EFFECTS If a role has no explicit row for a module, default to locked (deny-by-default), not visible — safer default for a hotel PMS handling guest PII and payment data. 3. Configuration as an In-App Route Configuration is mounted at its own route (e.g. /configuration/*) within the same application and shares the same session/auth context as the rest of the shell — there is no separate login, no token hand-off, and no second application boundary to secure. The route renders a different layout component (Configuration's own Property/Configuration/Setting/Miscellaneous nav) instead of the Main PMS sidebar, but every API call it makes still carries the same session token as the rest of the app, scoped by the same client_id. "Exit Configuration" is a plain client-side navigation to /dashboard — no redirect to a different origin, no session re-establishment. Practical implication for role checks: since Configuration is reached by the same role-gating as any other module (role_module_access, module_key = 'configuration'), a user without Configuration access simply can't route into it — enforce this both in the client router (hide/lock the link) and on the server (reject Configuration API calls from a role without access), since a client-only check is not a real security boundary. 4. Placeholder Modules For any module where module_registry.is_built = false, the shell's router shows the "Coming Soon" state client-side — the backend does not need a dedicated endpoint per unbuilt module.
