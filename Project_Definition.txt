StayOS PMS Main PMS Screen (Application Shell) Project Definition Documentation Document Type: Project Definition Module: Main PMS Screen / Shell Status: Draft v1.0 1. Purpose The Main PMS Screen is the authenticated home shell that property staff land on for all day-to-day operations, once a property has been set up. It is not one of the 11 functional modules itself — it is the persistent frame (global navigation + top bar + content area) that hosts 10 of them, and hands off to Configuration as a separate application for the 11th. This matches the architecture already described in the Configuration Project Definition: Configuration "is the Separate page getting redirect from the actual PMS... and an exit page to redirect back to Actual PMS." The Main PMS Screen is the "actual PMS" referred to there. 2. Scope Persistent global navigation exposing all 11 modules: Dashboard, Reservation, Front Desk, Rate & Availability, Audit, Business Channels, Guest, Housekeeping, Utility, Reports, Configuration. A top bar with property context (name, working date), the logged-in user's identity and role, and sign-out. Role-based visibility of menu items, driven by the existing role_privilege / app_user tables from Configuration. Cross-application handoff to and from the standalone Configuration app (built separately in Google AI Studio), including a secure way to carry the session across the app boundary. A lightweight registry of which of the 11 modules are actually built and routable today vs. still pending, so the shell can show a sensible placeholder instead of a broken link. 3. Out of Scope The internal screens of each of the 10 in-shell modules (Dashboard, Reservation, etc.) — each gets its own Project Definition/UI-UX/Backend/API documentation set when it's built, same as Configuration and Rate & Availability. Configuration's own internal navigation (Property/Configuration/Setting/Miscellaneous) — that lives entirely inside the separate Configuration app, already documented. Fine-grained, per-screen permission editing UI — Role & Privileges currently only stores a coarse Role Type; a true per-module permission matrix is flagged as a future addition, not built here. 4. Architecture Decision — One App, Two Layouts The Main PMS Shell and Configuration are built and deployed as a single application (the same AI Studio project), not two separate apps. "Configuration is a Separate page" (per the existing Configuration Project Definition) refers to it having its own distinct navigation and layout chrome — Property / Configuration / Setting / Miscellaneous, with its own Exit action — not to it being a separately hosted application. Both live behind the same login and the same session. Main PMS Layout — wraps Dashboard, Reservation, Front Desk, Rate & Availability, Audit, Business Channels, Guest, Housekeeping, Utility, Reports. Renders the persistent sidebar described in the UI/UX doc. Configuration Layout — a different layout component (its own top nav: Property/Configuration/Setting/Miscellaneous, plus an Exit Configuration action) mounted on its own route tree, e.g. /configuration/*. Both layouts read from the same auth context / session — there is no token hand-off between them, because there is no application boundary to cross. Clicking Configuration is an ordinary client-side route change to /configuration; clicking Exit Configuration is an ordinary route change back to /dashboard. 5. Success Criteria A logged-in user sees all 11 modules in the sidebar, with the 10 not-yet-built ones clearly marked (not broken links). Clicking Configuration client-side-routes into the already-built Configuration screens under the same session and property context, with no second login and no full page reload. Clicking "Exit Configuration" routes back to the Main PMS Screen's default view (Dashboard) within the same session. Menu visibility respects the user's role without requiring a page reload when role changes take effect.
